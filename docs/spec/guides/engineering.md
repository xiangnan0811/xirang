# 复用与跨层变更

## 确定归属再实现

修改前搜索相似函数、组件、常量及调用方。已有能力能够表达需求时，应复用或扩展。需要共享的校验、格式转换和常量放在既有职责层，避免复制后出现不同规则。

不要仅为消除一行重复增加复杂抽象。多个调用方共享相同语义、逻辑复杂或修复必须同步传播时，才提取公共实现；相似外观不代表同一职责。

## 明确数据边界

沿“来源 → 转换 → 持久化 → 查询 → 转换 → 展示”追踪完整链路，逐个明确：

- 输入、输出、缺失值及错误的表示；日期、枚举、ID 和不透明版本令牌不能依赖隐式转换。
- 哪一层拥有业务规则，以及入口校验、服务授权和数据库约束各自负责什么。前端校验不能替代服务端鉴权或持久化约束。
- 请求失败、取消、重试、并发写入和部分成功时，调用方如何恢复；不得静默覆盖现有状态。

组件使用 API 边界映射后的类型，不直接依赖数据库字段。跨层合同归对应[领域主文](../domains/README.md)，后端和前端通用规范只定义本层惯例。

## 验证边界与批量改动

覆盖空值、非法值、错误映射、持久化往返及消费者兼容。连续 CAS 操作必须用上一响应的新令牌发下一请求；测试应包含超过 JavaScript 安全整数范围的令牌。生产者和消费者的枚举测试应使用真实生产者生成的持久化值，明确语义转换并拒绝未知值。

批量改名或迁移后，重新搜索全部消费者，包括点目录配置、模板、脚本和手工清单。若两个入口承诺生成相同结果，但一个自动枚举、另一个手工列举，需测试结果集合一致，避免新建正常而更新漏项。

跨多个职责层、复杂数据表示或曾反复出错的流程，应在现有主文补充必要的数据流和失败路径；不为常规改动新建过程文档。验证原则见[测试约定](testing.md)。
