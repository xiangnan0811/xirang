## Gate Composition Review

### REST route layering

- Secured REST routes are grouped under `secured := v1.Group("")` and consistently apply primary auth, audit logging, API rate limiting, and max body size before route-specific gates (`backend/internal/api/router.go:126-130`).
- Primary HTTP auth rejects purpose-scoped tokens, so a `2fa_pending` or `step_up` token cannot be reused as a normal bearer token (`backend/internal/middleware/auth.go:21-54`).
- Role/permission gates are route-specific:
  - Admin-only surfaces use `RequireRole("admin")`, including credential audit list/export, settings, sensitive config import/export, task restore, snapshot restore, and several admin settings routes (`backend/internal/middleware/rbac.go:87-99`; `backend/internal/api/router.go:262-263`, `backend/internal/api/router.go:287`, `backend/internal/api/router.go:309`, `backend/internal/api/router.go:313-321`).
  - Operator/viewer permissions use `RBAC(permission)` (`backend/internal/middleware/rbac.go:99`).
- Ownership gates compose before step-up for per-object user-triggered task/node operations where applicable. Example: manual task trigger applies `RBAC("tasks:trigger")`, then `OwnershipTaskCheck`, then `RequireStepUp`, then handler (`backend/internal/api/router.go:282`). This means non-owners do not get a reusable step-up path for unauthorized objects.
- Batch command and batch trigger perform set-based ownership checks in handlers before executing work; batch command enforces step-up after ownership filtering and before command creation (`backend/internal/api/handlers/batch_handler.go:113`).

### Admin/operator/viewer representative cases

- Admin: Can access admin-only audit/settings/config/restore surfaces, but selected high-risk operations still require TOTP step-up. Sensitive config export also has a defensive handler-level admin check.
- Operator: Can access allowed node/task operations subject to ownership checks. For manual task trigger, ownership is checked before step-up. For batch trigger/command, handler-level filtering prevents non-owned targets from executing.
- Viewer: Has read-oriented permissions but lacks write/trigger permissions needed for high-risk task/batch command execution; admin-only surfaces reject viewer at backend regardless of frontend UI state.

### WebSocket flows

- WS routes are intentionally outside the secured HTTP group due to browser header limits (`backend/internal/api/router.go:363-365`).
- Realtime auth parses the first protocol token and rejects purpose-scoped tokens (`backend/internal/api/handlers/realtime_auth.go:19-28`).
- Terminal WS requires admin realtime auth and a valid step-up proof before node lookup/SSH auth/dial (`backend/internal/api/handlers/terminal_handler.go:193-226`, `backend/internal/api/handlers/terminal_handler.go:259`).
- Result: purpose-scoped primary auth is rejected, and terminal enforces protocol-level proof before high-risk SSH access.

### Direct-download/export flows

- SSH key export uses manual `fetch`, but still sends the same bearer token and step-up header as the central API wrapper (`web/src/lib/api/ssh-keys-api.ts:101-104`) and backend enforces RBAC plus route-level step-up (`backend/internal/api/router.go:228`).
- Credential audit CSV export uses backend admin-only route plus output-time sanitizer; frontend admin UI only exposes it to admin and uses the API export helper (`backend/internal/api/router.go:263`; `web/src/pages/credential-audit-page.tsx:201-205`, `web/src/pages/credential-audit-page.tsx:252-253`).
- Config export direct API bypass is handled by backend admin-only route and conditional step-up for `include_secrets=true`; default frontend component reviewed does not request sensitive export.

## Secret-safety Review

### Data model and normal API response safety

- `Node.Sanitized()` clears node password/private key and nested SSH key private key before API exposure (`backend/internal/model/models.go:47`).
- `SSHKey.PrivateKey` is JSON-omitted at model level and SSH key API response DTOs omit private key material while exposing allowed scope fields and derived public fields (reviewed in `backend/internal/model/models.go` and `backend/internal/api/handlers/ssh_key_handler.go`).
- Sensitive fields including SSH key private key, node password/private key, TOTP secret/recovery codes, task executor config, integration endpoints/secrets/proxies, and app credential config are handled by model hooks (reviewed in `backend/internal/model/models.go`).

### Credential audit write-time safety

- Credential audit write path caps metadata at 16 entries (`backend/internal/credentialaudit/audit.go:19`, `backend/internal/credentialaudit/audit.go:256`).
- Metadata keys and values are denied when they contain sensitive markers such as private/password/token/secret/credential/config/output/stream/command/content/payload, plus bearer/authorization markers for values (`backend/internal/credentialaudit/audit.go:265-276`).
- Error messages redact output/stdout/stderr markers (`backend/internal/credentialaudit/audit.go:296-303`).

### Credential audit read/export/UI safety

- Credential audit list/export maps every row through output-time sanitizer (`backend/internal/api/handlers/credential_audit_handler.go:294-313`).
- Export is bounded by max limit and allowed sort fields (`backend/internal/api/handlers/credential_audit_handler.go:24-31`, `backend/internal/api/handlers/credential_audit_handler.go:326-337`).
- Output metadata sanitizer re-applies key/value denial, bounds keys/values/lists, and redacts legacy sensitive text (`backend/internal/api/handlers/credential_audit_handler.go:359-518`).
- Frontend credential audit API sanitizer mirrors forbidden metadata markers and known action mapping (`web/src/lib/api/credential-audit-api.ts:54-96`, `web/src/lib/api/credential-audit-api.ts:161-224`).
- UI renders sanitized metadata from the client mapper (`web/src/pages/credential-audit-page.tsx:499-510`).

### Step-up proof handling

- Step-up proof is a purpose-scoped JWT generated with short TTL (`backend/internal/auth/jwt.go:21-30`, `backend/internal/auth/jwt.go:109-136`).
- Proof validation requires purpose `step_up`, same user, same role, current token version, and TOTP still enabled (`backend/internal/api/handlers/step_up.go:77-108`).
- Step-up audit stores proof state strings (`required`, `failed`, `satisfied`, `issued`, etc.) and operation context, not the proof token itself (`backend/internal/api/handlers/step_up.go:125-130`, reviewed metadata below that point).
- Frontend stores proof in `sessionStorage` and clears expired/invalid proof (`web/src/lib/step-up-storage.ts:40-67`), clears auth and proof on 401 (`web/src/lib/api/core.ts:135-140`), and clears proof on logout/TOTP disable/retry failure (reviewed in `web/src/context/auth-context-provider.tsx` and `web/src/hooks/use-step-up-action.ts:19-20`).

### High-risk metadata samples reviewed

- Task restore records `custom_target` boolean instead of target path (`backend/internal/api/handlers/task_handler.go:630`, `backend/internal/api/handlers/task_handler.go:644`).
- Snapshot restore records include count, target-set boolean, and a shortened snapshot ID (`backend/internal/api/handlers/snapshot_handler.go:147-148`).
- Config export audit stores sensitive-export boolean and object counts (`backend/internal/api/handlers/config_handler.go:228-236`).
- File browser audit uses path hashes/counts, not raw file paths/content (`backend/internal/api/handlers/file_handler.go:98-132`, `backend/internal/api/handlers/file_handler.go:183-253`).
- Batch command audit stores counts and retain flag, not command body/output (reviewed in `backend/internal/api/handlers/batch_handler.go`).
- Docker/doctor/preflight surfaces write stage/count/outcome-style audit metadata and use sanitizer-compatible event writes (`backend/internal/api/handlers/docker_handler.go:98-120`, `backend/internal/api/handlers/node_doctor_handler.go:193-201`, `backend/internal/api/handlers/node_migrate_preflight_handler.go:413-421`).

### Blocker before P2
