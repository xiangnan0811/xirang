# Research: Task 8 Managed Runtime, Settings And Metrics

- Query: Map Task 8 managed runtime, settings transitions, downgrade readiness, metrics, and main/router injection to the current code; identify RED tests, reusable seams, ordered implementation batches, and manifest drift.
- Scope: internal
- Date: 2026-08-12

## Findings

### Task contract and scope

Task 8 is specified by `implement.md:2225-2268` and `design.md` sections 9, 12, 13, and 15. It owns graph startup/publication after metadata reconciliation, sticky admission shutdown, recovery worker scheduling/wake/retry, the receipt-reaper owner, settings validate/drain/persist/install rollback, downgrade-readiness/fences, closed-label recovery metrics, and main/router narrow-facade injection. Task 6 may define restart reconciliation facts but cannot claim runtime composition or lifecycle proof (`implement.md:2155`, `research/current-main-evidence.md:404-405`).

### Existing runtime seams and reusable patterns

- The process-wide composition root is `backend/internal/backupasset/runtime/runtime.go:41-113` (`Dependencies`, manager interfaces, and `Runtime`). `Runtime.New` constructs Foundation, keyring, Repository/Provider, admission, and publication workers; main constructs it at `backend/cmd/server/main.go:126-143` and injects Task observers/readiness at `backend/cmd/server/main.go:206-229`.
- Current startup ordering is admission initialization, Content startup, publication `StartupPass`, health pass, unresolved-publication check, interrupted TaskRun readiness, search startup, then optional processing/export starts (`runtime.go:1511-1605`). This is the model for Recovery: reconcile metadata before publishing facades, and never execute queued restores synchronously during server startup. The current runtime has no Recovery facade/worker owner in its struct or startup/run/shutdown path.
- Existing managed Export is the closest lifecycle template. `managedExportPublication` is a shared publication gate with active-reference counting and `waitIdle` (`export_runtime.go:637-692`); graph publication/unpublication is explicit. `managedExportRuntime.Startup` rejects stopped/sticky-nonaccepting state and starts disabled maintenance without publishing (`export_runtime.go:1980-2028`). `TransitionSettings` uses transition and shutdown mutexes, unpublishes, waits idle, calls graph `stopAccepting`, drains/shuts down/closes, persists only after drain, and rebuilds the previous graph on failure (`export_runtime.go:2393-2495`). `StopAccepting` swaps an atomic accepting flag, marks not ready, unpublishes, cancels startup, and stops the graph (`export_runtime.go:2553-2585`). `Shutdown` repeats the sticky stop, waits startup, waits publication idle, shuts down graph, closes store, and joins (`export_runtime.go:2630-2675`). Reuse these semantics for Recovery rather than inventing a second graph protocol.
- Admission has a durable transition primitive. `admissionBarrier` tracks mode, generation, active tokens, transition/stopping flags and a change channel (`runtime/admission.go:299-313`). `transitionResolve` begins a transition, waits active tokens to drain, resolves/validates target, persists, then increments generation and publishes the mode (`admission.go:346-411`). `stopAccepting` is sticky and non-blocking; `stop` later joins active tokens (`admission.go:413-449`). The existing generation/token API (`admission.go:479-515`) is the natural fence source for downgrade readiness.
- Runtime shutdown currently calls `StopAccepting`, then Export, Processing, Content, Search, Catalog, publication, health, admission (`runtime.go:1755-1805`). Recovery must be inserted into this order with the design's stricter sequence: unpublish plan/ticket facades, stop claims, cancel/join attempts, fence source/node ownership, revoke/drain delivery, stop lifecycle; receipt owner must be joined before schema drain. Main currently closes worker/update listeners and calls `assetRuntime.StopAccepting` before HTTP shutdown (`main.go:383-401`); add Recovery to this same owner, with tests asserting no listener/graph publication before startup reconciliation and no shutdown ordering inversion.

### Recovery worker scheduling, wake, retry and reaper

- Recovery claim and takeover already have durable scheduler rows, separate scopes, CAS revision, cursor and finite high-water (`recovery/worker.go:336-369`, `:412-502`, `:504-594`, `:725-757`). Claim uses queued jobs with active source/node/attempt lease joins (`worker.go:372-389`); takeover uses expired lease predicates (`worker.go:391-410`). This directly satisfies the durable keyset/high-water scheduling direction and should be wrapped by a managed worker with a separate bounded retry/takeover deadline scheduler.
- Publication's wake pattern is reusable: `PublicationWorker.TryWake` is non-blocking, bounded, and returns false while stopping (`runtime/publication_worker.go:101-123`); periodic scans remain durable fallback (`publication_worker.go:24-26`, `:126-180`). Export's worker tests specifically prove queued work wakes before GC cadence (`runtime/export_runtime_test.go:4178`). Recovery job creation should expose a narrow `TryWake(jobID)` callback and test wake-before-long-cadence, retry scheduler deadline isolation, and no reliance on GC cadence.
- Receipt ownership is already implemented as a standalone narrow seam in `runtime/recovery_runtime.go:46-220`: `RecoveryAuthorizationReceiptOwner` validates Foundation cadence/batch, runs one immediate bounded pass, retries failed passes on subsequent ticks, forbids concurrent owners, and makes `Shutdown` sticky/idempotent. Tests already cover disabled admission, retry after failure, and join-before-schema-drain (`runtime/recovery_runtime_test.go:1-130`). However it is not composed into `Runtime`; Task 8 must add the owner dependency (Recovery authorization service), start it after Recovery metadata reconciliation, run it regardless of admission mode, and shut it down before migration/schema drain.
- Receipt deletion is a single transaction with one stateless indexed eligibility predicate (`recovery/service.go:3681-3745`). It filters proof/replay/session expiry, plan/requester linkage, and operation-specific grant expiry; normal evidence, protected rows, and latch rows cannot consume the LIMIT. Existing service tests cover restart and stale-row behavior (`recovery/service_test.go:1263-1323`, `:1800-1804`, `:1870-1950`). Do not add a mutable timestamp cursor or mutate ordinary evidence/latch rows.

### Settings transition and rollback seams

- Foundation already exposes typed recovery authorization settings and validates replay/grant coupling: registry keys are `settings/service.go:399-403`, grouped in `backupAssetRecoverySettingKeys` (`service.go:1694-1700`), parsed by `FoundationService.RecoveryAuthorizationConfig` (`backupasset/service.go:707-733`), and cross-field validation rejects write/delete grant TTL beyond replay TTL (`settings/service.go:1914-1918`). Task 8 must extend this same registry/foundation snapshot for the remaining Recovery settings (worker concurrency, leases/retries, result/cleanup caps, enabled/default root/locators), preserving complete snapshot fixtures.
- Settings handler already centralizes foundation mutation through `WithBackupAssetMutation` and `transitionBackupAssetSettingsMutation` (`api/handlers/settings_handler.go:88-124`, `:286-335`). BatchUpdate validates all keys before persistence; Delete/reset routes through the same transition owner; Config import normalizes/validates settings and invokes the same owner (`api/handlers/config_handler.go:66-114`, `:916`). Task 8 tests must prove all three paths use validate -> drain -> persist -> install and restore the old graph if drain, persist, or install fails. Current code currently parses only Export config in the runtime transition (`runtime.go:1397-1434`), so Recovery must be added without bypassing the existing owner or persisting first.
- Target-root locators are already encrypted/redacted via Foundation target-root service and `Sensitive` settings definitions (`backupasset/service.go:707+`, `settings/service.go:72-83`, target-root tests in `settings/service_test.go:1-530`). Tests must assert locator plaintext is not in settings responses/logs and that plaintext retained while disabled remains downgrade-unready.

### Downgrade readiness and mixed-version blockers

- Recovery reconciliation already has a bounded multi-root operation keyed by an opaque admission generation (`recovery/service.go:4206-4285`, `RecoveryDowngradeReconciliationRequest`). It paginates each configured root, returns `clear/blocked` counts/findings, and fails closed on invalid or incomplete cursors. Existing tests cover fresh all-roots clear and PostgreSQL (`recovery/service_test.go:6070-6315`). Task 8 must put this behind the current-binary Admin settings operation, require disabled feature, fresh `asset.recover` proof, bounded non-empty reason, idempotency key, and a sticky process-wide downgrade fence.
- The design requires snapshotting runtime and DB under one transition generation after joining mutation workers. Readiness is pristine only with no permanent use latch and zero queued/running jobs, unconsumed authorities, source/node leases, attempts, non-cleaned results, Content grants/tickets/streams, and cleanup/orphan/reconciliation backlog. A latch always produces `forward_fix_only`; no pre-Child process may be trusted to read 000069 (`design.md:1173-1238`, `:1435-1517`). Existing `schema_use_latch` and scheduler rows are migration-enforced (`000069` migrations and `recovery/testutil_test.go:1112-1121`).
- `admissionBarrier` generation increments only after a successful persisted transition (`admission.go:346-411`), so the downgrade receipt should bind to that generation and become invalid on re-enable. Add RED tests for default-disabled new backend/old frontend, new frontend/old backend, disable with retained plaintext, restart, latch-present, and forbidden pre-Child downgrade.

### Closed-label metrics

- Existing publication metrics use validated closed provider/stage/outcome/state labels (`backend/internal/backupasset/publication/metrics.go:1-220`); Content metrics similarly map provider/action/outcome/reason/cache labels to `unknown` for invalid values (`backend/internal/backupasset/content/metrics.go:1-220`). These are the pattern for Recovery metrics.
- `backend/internal/backupasset/recovery/metrics.go` and `metrics_test.go` are listed as future-create paths but are absent in this worktree. New Recovery metrics should expose only closed `provider`, `state`, `outcome`, and `category` labels; no repository/job/node/user/path/reason/error-string labels. Tests should inspect descriptor variable labels and invalid-value mapping to `unknown`.

### Main, router and content injection

- Router already receives narrow asset runtime facades and builds handlers from those (`backend/internal/api/router.go:80-165`, `:300-390`); secured routes consistently use `AuthMiddleware`, audit, rate limit and RBAC (`router.go:390-480`). The Recovery handler file is already present and owns proof/idempotency decoding (`api/handlers/backup_recovery_handler.go:1-180`), but Recovery routes are not registered in the visible router section.
- Main creates Runtime once, injects Task observers/readiness, runs `StartupPass`, and starts listeners (`backend/cmd/server/main.go:126-229`). Task 8 must expose narrow Recovery service/facade accessors from Runtime and pass them to Router/Content; handlers must not build a graph or read raw Recovery models. Startup tests should assert the Repository Rsync resolver and Target writer are injected and nil/unbound ports fail before publication, as explicitly required by `implement.md:1092-1099`.

## Smallest ordered implementation batches

1. **RED contracts and manifest ledger.** Amend the manifest bookkeeping for already-tracked nominal create paths; add focused RED tests in existing runtime/recovery/settings/main/router test files and the genuinely absent Recovery metrics tests. Cover graph publication ordering, nil/duplicate publication, queued-job startup non-execution, sticky StopAccepting, shutdown order, wake/retry/high-water, receipt owner lifecycle, and closed metric labels.
2. **Recovery managed graph composition.** Add Recovery graph/facade fields and constructors to `runtime.Runtime`; inject Repository resolver/Target writer and Recovery authorization service; reconcile metadata before publication; publish exactly once; start receipt owner after reconciliation; expose `TryWake` to job creation; add Run/StopAccepting/Shutdown joins in the required order. Keep same-binary disabled maintenance/lifecycle owner alive.
3. **Worker scheduling and lifecycle tests/implementation.** Wrap existing `WorkerCoordinator.ClaimNext`/`TakeoverExpired` with independent bounded retry/takeover scheduling, wake channel, and shutdown cancellation. Preserve scheduler rows/high-water semantics; prove no long-GC dependency and no startup restore execution.
4. **Settings transition integration.** Extend Foundation typed config/validation, then route BatchUpdate/Delete/reset/config import through one Recovery-aware validate -> drain -> persist -> install/rollback owner. Disabled mode fences new plans/security/authorities/jobs/writes while revoke/cleanup/orphan reconciliation continues; keep target roots encrypted/redacted.
5. **Downgrade readiness operation.** Add Admin settings transition owner operation with proof/reason/idempotency validation, sticky generation fence, worker joins, blocker aggregation, latch forward-fix-only result, and restart/mixed-version matrix. Reuse `ReconcileDowngradeReadiness`; never perform schema down inside readiness.
6. **Metrics and main/router/content closure.** Add Recovery closed-label Prometheus metrics and tests; register Recovery routes with existing auth/RBAC/ownership middleware; wire narrow facades through main/router/content; run backend focused/race, full backend, frontend and CI workflow selectors plus exact manifest/protected-path gates.

## Caveats / Not Found

- No `Recovery` runtime manager or Recovery route registration was found in the current `Runtime`/router composition; the existing handler and receipt owner are partial prerequisites, not proof of Task 8 completion.
- The current `ReapAuthorizationReceipts` predicate is stateless and correctly excludes protected/normal/latch rows, but it is ordered by replay expiry rather than an explicit `(replay_expires_at,id)` cursor; Task 8 should preserve the stateless indexed predicate and test restart fairness rather than introduce mutable cursor state.
- `Runtime.Shutdown` currently does not call the receipt owner because it is not composed. Schema-down nesting currently covers Export/Content/admission only (`runtime.go:1453-1467`); Recovery owner must be inserted before migration drain.
- The requested CI workflow change is listed in the modify manifest, but no Task 8-specific CI selector was found in the inspected sections; use existing backend/full recovery, race, PostgreSQL, frontend and manifest gates rather than inventing a new workflow path.
- External documentation was not needed; all findings are from the task artifacts and current Go code/tests.
