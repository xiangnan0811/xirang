# 备份数据资产浏览与预览功能设计

## Goal

在不削弱 xirang 现有备份、验证与恢复主链路的前提下，让用户能够理解、浏览和安全查看已经备份的数据，使“备份是否存在”进一步升级为“备份内容可见、可核验、可取用”。

本任务仅进行产品构想、竞品调研、现状审计和方案设计，不进入功能实现。

## User Value

- 用户可以确认一次备份实际包含了什么，而不只看到任务状态或统计结果。
- 用户可以直接预览常见备份内容，例如图片、文本配置和音视频，而不必先完整恢复到目标节点。
- 用户在故障、误删或审计场景中可以更快定位所需版本和文件。
- 产品将在“服务器运维备份闭环”基础上形成完整的数据资产访问能力，但保持备份资产浏览器而非通用网盘的数据写入/协作定位。

## Confirmed Facts And Intent

- 当前项目各项备份任务与监控正常运转；本次需求不是修复备份失败。
- 当前用户无法方便地查看已经备份的数据内容，至少缺少图片查看、配置文本查看和视频播放等体验。
- 用户认为备份数据不应只服务于恢复，还应支持查看等日常访问能力。
- Google Drive、OneDrive、百度网盘、阿里云盘等产品可作为交互和能力参考，但不能直接假设 xirang 应复制通用网盘的完整范围。
- 规划必须结合项目实际代码、数据模型、存储后端、权限与审计机制，并参考开源和商业产品。
- 代码审计确认当前并非完全没有文件能力：已有实时节点 SFTP 文本预览、未被前端使用的本地 Rsync 备份目录列表，以及 Restic 快照列表/路径搜索/差异/恢复；这些能力彼此割裂，且没有任何通用的备份内容读取、媒体预览或单文件下载链路。
- 当前 `/app/backups` 页面只展示备份可信度、健康度、存储使用和配置引导，没有备份资产入口，这直接造成“备份存在但用户不可见”的体验。
- 四类执行器的资产语义不同：Restic 有真实快照；Rsync/Rclone 通常是当前镜像，不天然提供历史版本；Command 没有产物契约。统一体验必须基于能力声明，不能假装所有任务都是网盘目录或版本仓库。
- 当前 `TaskRun` 没有产物、快照或恢复点关联；现有 `SnapshotFileIndex` 仅覆盖 Restic 的路径、大小和修改时间。
- 当前 JWT 通过 `Authorization` 请求头发送，原生图片/音视频/PDF导航无法直接携带该请求头；大文件预览需要短时资源票据、Range、限流和可选的受控缓存，而不能把会话 JWT 放入 URL。
- 竞品调研表明：网盘擅长预览/搜索/分享，备份产品擅长版本/选择性恢复，对象存储擅长权限/临时访问/Range。xirang 的机会是把三者组合为“带可信证据的只读备份资产浏览器”。

## Confirmed Product Decisions

- 用户已于 2026-07-12 审核并确认首轮可视化研究总览，对现状判断、市场模型和建议交汇定位均无异议。
- 产品核心定位采用“带可信证据的只读备份资产浏览器”：回答备份中有什么、对应哪个恢复点、是否可信、能否安全查看，以及如何最短路径下载或恢复。
- “Drive-like / 网盘式”描述的是好找、好看、好取的交互体验，不意味着建设通用网盘的数据写入与协作体系。
- 上传、在备份仓库中创建/编辑文件、协作文档、公共分享和桌面同步客户端不属于本产品方向；OCR、全文索引、文档转换和媒体转码属于只读查看的派生处理能力，已纳入由可选 Worker 承载的完整目标设计。
- 当前部署只有用户本人一个实际使用者。规划不需要为复杂组织审批、协作或细粒度共享流程投入过多设计，但不能因此移除服务端授权、路径隔离、内容安全、资源限制和审计基线。
- 用户明确不接受“先做最小 MVP、后续长期修补”的路线，要求预算充足前提下在设计阶段投入足够精力，形成覆盖完整目标能力的终态设计。
- 完整目标设计应覆盖 Rsync、Restic、Rclone 三类文件备份执行器；Command 在没有显式产物清单契约前保持不支持。允许将未来实现拆分为遵循同一终态架构的独立模块和风险门禁，但不得使用需要推倒重来的临时接口或浅层产品承诺。
- 用户选择“完整能力 + 可选处理 Worker”架构：缩略图、OCR、全文索引、Office/PDF 转换、恶意文件扫描和媒体转码均纳入终态设计，但由可插拔 Worker/外部工具提供；核心 all-in-one 必须能够独立运行并优雅降级。
- 可选 Worker 的能力发现、健康状态、任务队列、资源配额、失败隔离和版本兼容属于完整设计的一部分；未部署 Worker 时，基础浏览、浏览器原生预览、下载和恢复不能失效。
- 用户选择统一 `RecoveryPoint` 方案：每次可证明成功的文件备份运行都应关联一个明确恢复点；Restic 映射原生快照，Rsync/Rclone 增加版本化恢复点模式，并作为新任务的推荐行为。
- 现有 Rsync/Rclone 镜像任务必须保持兼容，界面明确标注“可变当前镜像、非历史恢复点”，并提供可预检、可回滚的版本化迁移路径；不得伪造历史版本或把一次运行记录等同于不可变内容。
- `TaskRun`、`RecoveryPoint`、资产清单/索引、验证证据、恢复/下载操作之间必须建立可追溯关联；不可变恢复点只有在产物提交和最低限度清单验证完成后才可标记为可浏览/可恢复。`mutable_head` 只有在一次成功 observation 产生 source fingerprint 与原子激活的 Catalog generation 后才可读，且始终标注可变、观测时间和 freshness，禁止宣称 committed、immutable 或可信历史。
- 官方语义与代码适配调研确认：Rsync 版本化默认可采用空 staging 树、`--link-dest` 复用上一已提交树和同文件系统原子发布，但必须预检硬链接/挂载约束、禁止 `--inplace`，并区分“Xirang 管理的不可变”与存储 WORM。
- Rclone `--backup-dir` 仅保存一次同步中被覆盖/删除的旧对象，不能独立还原任意恢复点；跨后端的推荐默认是每个恢复点使用唯一且永不复写的版本前缀，并在远端清单校验后以提交清单发布。后端原生对象版本只在适配器能证明版本 ID、生命周期和精确重建能力时作为优化模式。
- 用户于 2026-07-13 审核并确认终态架构骨架：底层 Rsync/Restic/Rclone 通过适配器发布统一 `RecoveryPoint`；可重建的 Catalog Plane 与按需再授权的 Content Plane 分离；原生媒体使用短时资源票据；可选 Worker 只增强目录/内容能力，不进入备份提交和可信主链；无 Worker、无 Range 或仓库离线时必须按图示优雅降级。
- 用户选择“分层安全物化”策略：小型或顺序内容优先在有界内存中处理；大型可寻址内容使用独立认证分块、专用配额目录和每次启动随机内存密钥的加密临时缓存；外部 Worker 只有在必须使用文件路径时才可进入严格限额的专用 `tmpfs`，并要求宿主机禁用或加密 swap。
- 缓存策略必须提供全局禁用开关、每对象与总量配额、空闲与绝对 TTL、作业租约、启动及周期清理、派生物版本绑定、重新授权和安全遥测；不得静默回退到普通明文磁盘目录。原件、缩略图、OCR 文本、转换文档和转码媒体采用同一敏感等级、权限、加密与保留规则。
- 用户选择“实用最小权限”访问模型：新增彼此独立的备份资产列目录、预览和原件下载权限；Admin 可访问全部资产，Operator 仅可列出和预览其拥有节点/任务的资产且默认不可下载原件，Viewer 仅能查看备份健康和状态，不得看到文件名、路径、搜索片段或内容。
- 已获授权的普通预览无需重复二次验证；疑似秘密文件的内容揭示以及每次原件下载授权需要可复用五分钟的 TOTP step-up proof。基础设施恢复继续沿用更强的 Admin + step-up + 填写理由 + 任务/动作绑定限时授权。敏感分类只能增加警告或验证强度，绝不能放宽 RBAC、所有权、票据或审计。
- 用户选择将现有 `/app/backups` 升级为完整备份工作区，内部采用可深链接的“概览 / 数据资产 / 恢复与演练”三个视图；不得新增一个与“备份”含义重叠的一级侧栏入口，也不得继续把完整资产体验局限在 Tasks 弹窗中。
- `Tasks` 保持负责配置、调度、执行、重试和运行日志；备份工作区负责恢复点、目录、搜索、预览、下载与选择性恢复；实时节点文件浏览继续表示源节点当前状态，并在产品文案与导航上始终和备份副本区分。
- 用户选择自适应三栏“调查工作台”作为数据资产主布局：桌面端左栏常驻任务、恢复点和目录上下文，中栏提供可切换列表/网格的文件结果，右栏提供预览、元数据、版本与安全检查器；选中文件、路径、恢复点和筛选条件均可深链接。
- 窄屏不得压缩三栏，而应转换为“上下文选择器 → 文件列表 → 全屏预览”的连续流程；关闭预览或在前后文件间切换不能丢失当前任务、恢复点、目录、搜索条件和滚动位置。面板宽度、列表列宽和视图偏好可本地记忆。
- 用户选择完整的只读资产管理范围：纳入权限感知的跨任务全局搜索、保存搜索、收藏、用户标签、最近访问、批量选择、异步加密打包下载，以及受限归档目录浏览与单项取回；这些能力服务于备份资产的定位、组织和安全取用，不改变“只读备份资产浏览器”的产品边界。
- 保存搜索、收藏、标签和最近访问是 Xirang 中的用户侧元数据，不得写回、重命名或改变备份仓库内容；删除这些元数据不得影响恢复点及其可信证据。全局搜索和所有搜索片段必须先做权限与所有权过滤，Viewer 不得借搜索、计数、建议词或最近访问获知资产存在性。
- 批量取回采用异步导出作业，而不是在 Web 请求中同步拼装大文件：选择集在授权时固化并绑定具体恢复点，服务端按配额生成加密临时归档，完成后签发短时下载票据；作业状态、失败项、有效期、下载和清理均需审计。归档浏览必须有深度、条目数、展开大小、压缩比和处理时限上限，默认只允许在沙箱中查看目录并单项取回，不允许原地执行或无界解压。
- 用户接受全局搜索的混合范围：默认搜索每个已授权任务最新的已提交、仍保留 `RecoveryPoint`；遗留 Rsync/Rclone 镜像使用其唯一 `mutable_head`。用户可一键切换到全部已提交且仍保留的历史恢复点，范围选择可深链接并可保存，禁止用最新 `TaskRun` 或“最近已索引的旧恢复点”冒充当前结果。
- 全历史结果按任务/来源谱系与提供者语义下的规范路径分组，默认展示最新匹配版本、匹配版本数及首次/最后出现时间，展开后查看具体恢复点；同路径或同哈希不得跨任务直接合并，只有强内容摘要一致时才能标记内容相同。
- 核心 Catalog 必须为所有保留恢复点提供名称、路径和基础元数据搜索；正文、OCR 等增强字段只在相应 Worker 索引完成时参与，结果必须标记命中字段、索引代次和请求范围覆盖率。最新恢复点尚未完成索引时必须返回部分覆盖，只有请求范围全部完成对应索引后才能明确宣称“无结果”。
- 搜索结果、分组、计数、建议词和片段必须在服务端完成权限及所有权过滤后生成。疑似秘密文件在没有有效五分钟 step-up proof 时，必须从正文/OCR 匹配、计数、摘要与建议中整体排除；仅隐藏片段仍会泄露秘密存在性。路径命中继续按资产列目录权限处理。
- 与提交清单一致的不可变恢复点 Catalog 在仓库离线时仍可搜索，但必须标注内容暂不可用；`mutable_head` 搜索结果必须展示索引观测时间和陈旧状态。SQLite 与 PostgreSQL 必须保持一致的规范化、稳定排序、游标分页和覆盖度语义。
- 用户选择完整的跨重启异步导出语义：运行中的批量导出在 Xirang 重启后必须通过持久作业状态、租约/围栏令牌和输出校验安全恢复或重试；已密封完成的加密归档在绝对有效期内继续可下载，不能因正常升级或意外重启无提示消失。
- 每个导出使用独立随机 DEK 对归档进行流式/分块认证加密，DEK 由持久应用 KEK 包装并支持密钥轮换读取；启动对账不得仅凭残留文件推断作业成功。删除包装 DEK 应先完成密码学撤销，再由幂等 GC 清理物理密文。该持久导出密钥体系与预览缓存隔离，后者仍使用每次启动随机密钥并在重启后失效。
- 用户选择从资产调查到基础设施写入的“受控恢复计划”：单文件、目录和批量选择首先固化为绑定精确 `RecoveryPoint` 与 manifest entry 的恢复选择集，经过 Provider 能力、源可用性、目标节点/路径、容量、运行冲突、现有文件、符号链接、风险状态和预计变更预检后，才可创建持久 `RecoveryJob`；禁止使用 `latest` 或在执行时重新解释可变搜索结果。
- `mutable_head` 的恢复选择还必须冻结 typed observation revision（source fingerprint、Catalog generation 和 observed_at）；该 revision 进入 plan digest、授权 grant 和作业 checkpoint，并在预检、授权、首次写入、恢复续跑的前后重验，任何变化都必须 supersede/阻断或在已经写入后进入 needs_attention，禁止仅凭稳定 RecoveryPoint ID 恢复已变化的内容。
- 默认恢复目标是为本次请求创建的安全隔离目录，不默认回写源路径，也不得把 Provider 的 `sync`/`restore` 默认行为直接暴露为统一语义。隔离恢复完成后必须提供逐项成功、失败、跳过、摘要校验和差异报告，并允许用户在验证后下载、保留、清理，或另行发起原路径恢复。
- “恢复到原路径”是独立高风险模式：必须显式选择失败即停、跳过已有、覆盖选中项或精确镜像等冲突策略；默认策略为遇到冲突失败，不得默认删除目标端额外文件。执行前展示最终变更清单，并要求 Admin、fresh step-up、理由以及绑定任务、恢复点、选择摘要、目标、冲突策略和动作的限时授权。检测到恶意内容、源版本变化、目标预检漂移或节点运行冲突时必须重新授权或阻断。
- 用户选择将 `BackupRepository` 建模为独立于 Task 的一等资产：Task 负责配置、调度和执行，可有多个 Task 向一个仓库发布；仓库负责稳定身份、Provider 类型、非秘密定位、接入/凭据绑定、能力状态、恢复点集合与保留边界；`RecoveryPoint` 的任务/运行血缘可以在原 Task 归档或清理后以不可变摘要继续存在。
- 删除 Task 只停止未来调度、解除写入关联并保留既有仓库与恢复点，不得隐式删除 Provider 数据、Catalog、收藏或恢复能力。断开仓库只撤销当前接入并标记内容离线；物理清除仓库或恢复点必须是独立的 Admin + fresh step-up + 理由 + 影响预览 + 保留/租约/WORM 预检操作，并联动派生物、导出、票据和用户侧引用的既定清理语义。
- 系统必须提供显式的仓库重新接入/导入流程：Restic 通过非秘密仓库身份、重新提供的凭据和可归属快照证据登记；Xirang 管理的 Rsync/Rclone 通过保留的仓库标记、提交清单与 manifest digest 重建；遗留镜像只能登记为 `mutable_head` 或经过验证的 `imported_baseline`。不得扫描任意目录/Remote 后猜测恢复点血缘，也不得把缺少提交证据的普通文件树标成可信历史。
- 数据库丢失后的重建只能恢复 Provider 中可证明的仓库事实、恢复点、清单和派生 Catalog；保存搜索、收藏/标签、最近访问、授权与审计等仅存在于控制面数据库的状态，必须依赖 Xirang 数据库/配置及 `DATA_ENCRYPTION_KEY` 备份恢复，不能宣称可从备份仓库自动重建。
- 用户选择增强处理的最终完整覆盖策略：所有已提交、仍保留且符合格式/大小/安全策略的恢复点，最终都应完成相应 OCR、全文提取、缩略图、文档转换、恶意扫描和媒体派生处理；路径、名称和基础元数据 Catalog 仍是核心同步覆盖，不依赖 Worker。
- 增强处理调度必须保证交互请求与最新恢复点优先，近期历史随后，较老历史使用可暂停、可限速的低优先级回填资源池；备份提交、验证、恢复和用户主动预览必须拥有独立保留槽，后台回填不能造成饥饿或改变备份健康。管理员可以按 Provider、任务和 capability 查看覆盖率、积压、失败原因、预计完成时间并调整配额。

- 定义目标用户、核心场景、完整终态信息架构、功能边界、交付模块和明确的非目标。

### Candidate User Capabilities

以下为完整目标设计需要覆盖的核心能力；高级派生处理通过可选 Worker 承载，并具备未部署时的明确降级路径：

- 按节点、备份任务、执行记录、时间版本和目录层级浏览备份资产。
- 对每个恢复点展示提供者、不可变/可变状态、关联运行、提交状态、清单状态、校验/演练证据和保留到期信息。
- 查看文件名、路径、类型、大小、修改时间、校验状态、来源和备份版本等元数据。
- 预览文本/配置、图片、PDF、音频和视频；对不支持的类型提供安全下载或恢复入口。
- 搜索、过滤、排序、跨恢复点版本对比和收藏等网盘式只读能力；不包含公共分享。
- 在服务端权限过滤后跨任务、节点、提供者和恢复点进行全局搜索；支持保存搜索、收藏、用户标签和最近访问，并清晰区分用户侧组织元数据与备份事实元数据。
- 支持跨目录批量选择、选择集复核和异步加密打包下载；导出必须固定恢复点版本、显示逐项结果、受资源配额与有效期控制，并可被取消和审计。
- 对 ZIP、TAR 及经安全评估允许的归档格式提供受限目录浏览和单项取回；遇到加密归档、格式不支持、疑似压缩炸弹或资源超限时必须明确降级为原件下载或恢复。
- 从单文件取回到整批恢复的连续操作路径。

### Safety And Operations

- 预览与下载必须复用或强化现有认证、RBAC、资源归属和审计机制。
- 缩略图、OCR/全文搜索片段、转换文档和转码媒体均按“预览内容”授权；目录列表、预览票据、原件下载票据和恢复操作必须在服务端分别校验权限与所有权，禁止复用当前过宽的 `tasks:read`。
- 设计需覆盖秘密配置泄露、路径穿越、恶意文件、内容嗅探、压缩炸弹、超大文件、视频 Range 请求、临时文件和缓存清理等风险。
- 加密临时缓存不得复用现有面向小型数据库字段的整值加密格式，也不得落入会被持久化或再次备份的 `/data`、`/backup`、`/logs`；进程崩溃残留必须在密钥失效后不可解密，并由启动/周期协调器清理。
- 查看能力不得破坏备份产物、校验可信度、保留策略或恢复可用性。
- 方案需说明大规模目录、远程存储、网络开销、并发与失败降级策略。
